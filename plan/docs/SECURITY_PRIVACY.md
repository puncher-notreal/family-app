# Child safety, security and privacy — v0.1

**Это план инженерных мер, не юридическое заключение.** Для продукта, собирающего личные сведения детей, обязательны правовое заключение и проверка требований магазинов перед публичным релизом.

## 1. Что защищаем
- Детские оценки, школьные замечания и успеваемость; фото выполненных работ; настроение и частные комментарии; желания, семейные роли и сведения об устройствах.
- Никакой рекламы, публичных аккаунтов, общения с незнакомцами, геолокационного трекинга, открытого поиска детей.
- В MVP **без стороннего AI API**, поэтому комментарии ребёнка не уходят LLM-провайдеру.

## 2. Регистрация и вход
- Пароли взрослых: argon2id с актуальными параметрами и уникальными salts; rate-limits на login, reset, register; generic responses для неизвестного email; подтверждение адреса.
- PIN ребёнка: **не пароль и не публичный постоянный идентификатор**. Код 6 цифр генерируется криптографическим RNG, действует ~10 мин, привязан к конкретному child profile, принимается один раз, хранится как keyed HMAC с секретом сервера; лимит ≤5 неверных попыток + IP/device rate-limit. Успешный ввод создаёт **только pending pairing request**. Родитель подтверждает конкретное устройство; до подтверждения child session не выдаётся.
- Поскольку UX требует ввод только 6 цифр, использовать keyed HMAC для поиска активного кода, недопущение коллизий среди активных кодов, строгие глобальные/IP/device лимиты и **обязательное подтверждение запроса взрослым** (не доверять одному совпадению PIN). Код не даёт доступа сам по себе.
- Привязка device создаёт child session с серверным refresh-token hash, expiry и rotate/revoke. Токены хранятся в SecureStore/Keychain, при потере устройства взрослый отзывает доступ.
- При обнаружении повторного refresh-token/replay аннулировать семейство токенов; все private endpoints имеют auth guard.

## 3. Family-level authorization
- `owner`: всё по своей семье, управление участниками и согласиями.
- `co_parent`: дневник, задания, магазин, баллы, график настроения, дети; **не** переоформляет владельца без отдельной процедуры.
- `helper`: только назначенные права на задания; по умолчанию **нет** доступа к оценкам настроения, школьным данным и устройствам ребёнка.
- Child: только свой `childId`; нет API доступа к другой семье/ребёнку, редактированию оценок, админским действиям или баллам.
- Приглашение родственника не автоматически доказывает наличие законных прав родителя/опекуна. Возраст и полномочия лица требуют отдельной проверки; старший брат/сестра может быть младше 18.

## 4. Дневник и настроение
- `school_grades` append-only со стороны ребёнка; parent-update/delete проверяется на сервере + обязательный audit.
- Комментарии о настроении — приватные. Рекомендовано envelope encryption на уровне API + ключи из менеджера секретов (Vercel environment variables / Supabase Vault). Админские SQL-пользователи не должны иметь прямого повседневного доступа к расшифровке.
- Parent mood endpoint возвращает **только date + score** и вычисленную статистику, никогда raw comment/emoji. Не включать чувствительные тексты в push, логи, Sentry/analytics/crash services или URL.
- Никаких психологических диагнозов/рейтингов, «обнаружения депрессии» или автопередачи скрытого комментария. В будущем AI требует нового consent, возрастных safeguards, safety review, механизма объяснения и безопасного маршрута помощи.
- UI для ребёнка объясняет, что родитель видит оценку 1–10, но не личный комментарий; если продукт решит изменить это, нужен отдельный явный выбор и уведомление.

## 5. Файлы и медиа
- Только **Supabase Storage private buckets**. Форматы JPEG/PNG/HEIC с безопасной серверной конвертацией; максимальный размер/количество, проверка file magic/MIME и malware scanning по утверждённому уровню.
- EXIF/GPS scrub до постоянного сохранения, не хранить абсолютные пути, не раскрывать storage keys в API.
- Скачивание через серверную авторизацию и короткоживущий signed GET. Удаление файла по retention и при соответствующем запросе удаления.
- В metadata: `familyId, ownerChildId, uploadedByActor, purpose`, состояние `pending/ready/rejected`.

## 6. Локализация и правовые gates — целевые рынки
- Правовая проверка проводится для каждого целевого рынка перед запуском: GDPR (ЕС: правовые основания, согласие законного представителя, права субъекта, DPA с Vercel/Supabase), COPPA (US: verifiable parental consent, ограничения на сбор данных детей до 13), плюс требования юрисдикций локального хранения данных, если продукт запускается на таких рынках (например РФ — 152-ФЗ; Китай — PIPL).
- До запуска: определить контролёра данных (data controller), основания обработки, согласия/права законного представителя, документировать процессы и передаваемые данные, положения о безопасности и удалении.
- Регион хранения Supabase-проекта выбирать под целевой рынок (data residency) и зафиксировать в ADR; оценку использования push, облачных сборок (EAS), e-mail, телеметрии, CDN, crash reporting и будущего AI провести до запуска.
- Подготовить политику, пользовательское соглашение, механизм отзыва согласия/удаления, контакты контролёра данных и возрастные условия.

Источники: https://gdpr.eu/ , https://www.ftc.gov/business-guidance/privacy-security/childrens-privacy

## 7. Требования магазинов
- Проверить Kids Category, родительские ворота для внешних ссылок, возрастные ограничения 7–12 лет, наличие фото/возможности пользовательского контента, требования к privacy, data safety и отсутствию рекламных SDK.
- Apple имеет требования для Kids Category к сторонней аналитике, рекламе, ссылкам и раскрытию передачи данных третьим сторонам; Google Play Families требует корректного декларирования детской аудитории и сбора данных.
- Договориться о финальной категоризации и текстах до подачи сборки, не рассчитывать на формальную «обходную» классификацию как взрослое приложение.

Источники: https://developer.apple.com/app-store/review/guidelines/ , https://developer.apple.com/kids/ , https://support.google.com/googleplay/android-developer/answer/9893335?hl=en

## 8. Удаление данных
- Взрослый может удалить свой аккаунт, но удаление общей семьи — отдельное действие для владельца, где показаны последствия для других членов.
- Документировать retention и условия удаления ребёнка/семьи, экспорт/доступ к данным, подтверждение полномочий, удаление из БД/Storage/кэшей/очередей/backup по утверждённым срокам; не обещать немедленное физическое стирание всех backup без доказанного процесса.
- При удалении/отзыве доступа сначала аннулировать сессии, затем запустить контролируемый workflow и записать событие аудита без чувствительного контента.

## 9. Security acceptance gates
- Невозможность cross-family доступов при подмене family/child/grade/task/media IDs.
- PIN: 6 digits + rate limits + expiry + one-time + revocation + reset, без plaintext в logs.
- Тесты IDOR для всех GET/POST/PATCH/DELETE и signed URL.
- Одновременный approve не выдаёт двойные баллы; redemption не уводит balance ниже 0.
- Parent mood API JSON не содержит comment ни в каких состояниях.
- Android/iOS secure token persistence; logout и отзыв устройства закрывает новые запросы.
- Статические проверки зависимостей, secret scanning, резервное копирование/restore drill (Supabase backups/point-in-time recovery), правовая приёмка до prod.
